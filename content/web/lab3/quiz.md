### Вопрос 1

Что делает JIT-компилятор в JVM?

- [ ] Находит в куче недостижимые объекты и освобождает их память
- [ ] Переводит исходный код из файлов `.java` в байт-код файлов `.class`
- [ ] Подгружает классы при первом обращении к ним и проверяет их байт-код
- [x] Компилирует часто вызываемые методы в машинный код во время работы программы

**Разбор:** JIT (Just-In-Time) превращает «горячие» методы в машинный код с оптимизациями по реальной статистике вызовов, поэтому первые запросы к серверу медленнее тысячного. В байт-код исходник переводит `javac`, классы подгружает загрузчик классов, а память освобождает сборщик мусора.

**Где в учебнике:** вопрос 1 «Java в серверной веб-разработке. Особенности языка и платформы JVM»

### Вопрос 2

Что из перечисленного характерно для Spring Boot, а не для варианта Jakarta EE на Open Liberty?

- [ ] Набор стандартных спецификаций, которые реализуют разные производители серверов
- [x] Встроенный сервер и исполняемый fat JAR, который запускается командой `java -jar`
- [ ] Приложение собирается в WAR и разворачивается на отдельном сервере приложений
- [x] Автоконфигурация: бины создаются по содержимому classpath и заданным свойствам

**Разбор:** в Spring Boot приложение содержит сервер: стартеры, автоконфигурация и встроенный Tomcat едут внутри fat JAR. В Jakarta EE наоборот: это набор спецификаций, сервер приложений уже содержит их реализации, а приложение собирается в WAR и без сервера не запускается.

### Вопрос 3

Чем абстрактный класс отличается от интерфейса в Java?

- [ ] Абстрактный класс можно создать через `new`, а объект интерфейса создать нельзя
- [ ] В интерфейсе нельзя написать ни одного метода с реализацией, в абстрактном классе — можно
- [ ] Класс реализует только один интерфейс, но может наследовать несколько абстрактных классов
- [x] У абстрактного класса могут быть поля с состоянием и конструктор, у интерфейса — только константы

**Разбор:** поэтому `ApiException` в работе — абстрактный класс: ему нужны общие поля `status`, `code`, `details` и конструктор, который вызывают наследники через `super(...)`. Наследовать можно только один класс, а реализовать — сколько угодно интерфейсов. Абстрактный класс через `new` не создаётся, а в интерфейсе с Java 8 есть `default`-методы с реализацией.

**Где в учебнике:** вопрос 3 «ООП в Java: классы, интерфейсы, наследование и полиморфизм»

### Вопрос 4

Какой `@Retention` нужен аннотации, чтобы фреймворк прочитал её во время работы через рефлексию?

- [ ] `RetentionPolicy.SOURCE`
- [ ] `RetentionPolicy.CLASS`
- [x] `RetentionPolicy.RUNTIME`
- [ ] Никакой: без `@Retention` аннотация и так доступна во время работы

**Разбор:** только `RUNTIME` загружает аннотацию в память JVM, где её видит рефлексия. `SOURCE` живёт лишь в исходнике (`@Override`), а `CLASS` — значение по умолчанию: аннотация есть в `.class`, но JVM её не загружает. Поэтому аннотация без `@Retention` фреймворку не видна.

**Где в учебнике:** вопрос 4 «Аннотации в Java и их использование в серверных приложениях»

### Вопрос 5

Что такое внедрение зависимостей (DI)?

- [ ] Принцип, по которому фреймворк сам вызывает код приложения в нужный момент
- [ ] Правило, по которому бин создаётся один раз и обслуживает все запросы приложения
- [ ] Код, который контейнер выполняет вокруг вызова метода бина, например транзакция
- [x] Объект не создаёт и не ищет свои зависимости, а получает их извне от контейнера

**Разбор:** «фреймворк сам вызывает код приложения» — это инверсия управления (IoC) в целом, а DI — её частный случай. Код вокруг вызова метода — интерсептор, «один бин на всё приложение» — область видимости `@ApplicationScoped`.

Куда ставится внешний ключ при связи один-ко-многим, например «пользователь — его refresh-токены»?

- [ ] В отдельную таблицу связи с парами «пользователь — токен»

### Вопрос 10

Что в JPA называют dirty checking?

- [ ] Перед сохранением провайдер проверяет поля сущности по аннотациям `@Column(nullable, length)`
- [ ] Повторный `find` по тому же ключу в транзакции возвращает тот же экземпляр без запроса к базе
- [ ] В конце транзакции провайдер отсоединяет объекты, и их изменения больше не отслеживаются
- [x] При фиксации транзакции провайдер сравнивает управляемые объекты со снимком и выполняет `UPDATE` для изменённых

**Разбор:** благодаря dirty checking в репозиториях работы нет метода `update`: достаточно изменить поля managed-объекта внутри транзакции. Повторный `find` без запроса к базе — кэш первого уровня, отсоединение объектов — переход в состояние detached. Атрибуты `@Column` — не валидация, они нужны только при генерации схемы по аннотациям.

### Вопрос 13

От чего защищает подпись JWT?

- [ ] От чтения: без секрета payload не раскодировать
- [ ] От использования токена, который сервер уже отозвал
- [x] От изменения содержимого, но payload может прочитать любой
- [ ] От предъявления токена не тем клиентом, которому его выдали

**Разбор:** header и payload закодированы Base64URL — это кодирование, а не шифрование, поэтому в payload нельзя класть пароли и хеши. Подпись лишь подтверждает, что токен выпустил сервер и его не меняли; об отзыве она ничего не говорит — для этого refresh-токены учитываются в базе по `jti`.

### Вопрос 14

Что такое RBAC?

- [ ] Доступ к записи разрешается, если её владелец совпадает с пользователем из токена
- [ ] У каждого объекта свой список «субъект — права»
- [x] Права назначаются ролям, а пользователю назначается роль
- [ ] Решение принимается по атрибутам субъекта, объекта и окружения

**Разбор:** RBAC (Role-Based Access Control) — модель работы: ADMIN меняет студентов, USER только читает. Свой список «субъект — права» у каждого объекта — ACL, решение по атрибутам — ABAC, сравнение владельца записи с пользователем — проверка владения, которая закрывает IDOR и делается в сервисе.

### Вопрос 15

Зачем при хешировании паролей нужна соль?

- [ ] Чтобы хранить вне базы общий секрет, без которого перебор невозможен
- [ ] Чтобы сервер мог при необходимости восстановить пароль пользователя
- [x] Чтобы хеши одинаковых паролей различались и радужные таблицы стали бесполезны

### Вопрос 1

Что может произойти при работе такого сервиса под нагрузкой?

```java
@ApplicationScoped
public class StudentService {
    private Student current;

    public StudentResponse replace(String isuId, StudentRequest request) {
        current = findOrThrow(isuId);
        StudentMapper.copyToEntity(request, current);
        return StudentMapper.toResponse(current);
    }
}
```

- [ ] Ошибка будет возникать на каждом втором запросе, поэтому её сразу поймают тесты
- [ ] Ничего: CDI создаёт отдельный экземпляр `@ApplicationScoped`-бина для каждого HTTP-запроса
- [ ] Код не скомпилируется: в `@ApplicationScoped`-бине нельзя объявлять изменяемые поля
- [x] Параллельный запрос перезапишет поле, пока первый с ним работает, и данные одного студента запишутся в другого

**Разбор:** запросы обрабатываются по модели «поток на запрос», а `@ApplicationScoped`-бин один на всё приложение, и его поля видят все потоки сразу. Ошибка проявляется редко и только под нагрузкой. Всё, что относится к запросу, должно жить в локальных переменных — в стеке своего потока.

**Где в учебнике:** вопрос 1 «Java в серверной веб-разработке. Особенности языка и платформы JVM»

### Вопрос 2

Почему в `pom.xml` работы зависимость `jakarta.jakartaee-api` объявлена со scope `provided`?

- [ ] Со scope `provided` Maven скачивает библиотеку не при сборке, а при первом запуске сервера

### Вопрос 3

В сущности `Student` объявили метод сравнения по ИСУ:

```java
public boolean equals(Student other) {
    return isuId.equals(other.isuId);
}
```

Что не так с этим кодом?

- [ ] Это переопределение, но без парного `hashCode` метод вызываться не будет
- [ ] Код не скомпилируется: параметр `equals` обязан иметь тип `Object`
- [ ] Метод сработает, но только для объектов из одного контекста персистентности
- [x] Это перегрузка, а не переопределение: коллекции и JPA вызовут `equals(Object)` из `Object`

### Вопрос 4

Администратор отправляет `POST /api/requests`, где ФИО из трёх букв, группа `M33011`, а общежитие `abc`. Все три поля нарушают аннотации Bean Validation на `StudentRequest`. Что получит клиент?

- [ ] 500, потому что валидатор бросил `ConstraintViolationException`
- [ ] 400, потому что тело не прошло проверку формата
- [ ] 422 с сообщением только о первом найденном нарушении
- [x] 422 с одним сообщением, где в `details` перечислены все три поля

**Разбор:** `validator.validate(body)` не бросает исключений, а возвращает множество нарушений. `RequestValidator` в работе собирает их все, переводит имена полей в snake_case и бросает одно `DataValidationException`, которое маппер превращает в 422 со списком полей. Так клиент сразу видит все ошибки формы.

**Где в учебнике:** вопрос 4 «Аннотации в Java и их использование в серверных приложениях»

### Вопрос 5

Почему зависимости обычно советуют внедрять через конструктор, а не через поле? Что при этом нужно учесть для `@ApplicationScoped`-бина CDI? Выберите верные доводы.

- [ ] Внедрение через поле в `@ApplicationScoped`-бине не работает, поэтому нужен конструктор
- [x] Поля зависимостей можно сделать `final`, а без зависимостей объект не создать
- [ ] С внедрением через конструктор бин создаётся при старте, а не лениво при первом вызове
- [x] В модульном тесте сервис создаётся обычным `new` с заглушкой, без контейнера
- [x] Для прокси `@ApplicationScoped` нужен ещё не-`private` конструктор без аргументов

### Вопрос 1

`AuthService.refresh` в работе выглядит так:

```java

    if (stored.isRevoked()) {
        refreshTokens.revokeAllOf(stored.getUser());
        throw new UnauthorizedException("INVALID_TOKEN", "Refresh-токен уже использован или отозван. Войдите заново");
    }

    stored.setRevoked(true);
    return issueTokens(stored.getUser());
}
```

Что изменится, если убрать `dontRollbackOn`? Выберите верные доводы.

- [ ] Ничего: `@Transactional` откатывает транзакцию только на checked-исключениях

- [x] Исправление — весь PATCH в одном `@Transactional`-методе сервиса и `@Version` у сущности

**Разбор:** ответ на защите: `service.get` читает без транзакции, `service.replace` пишет в своей, а слияние идёт между ними в HTTP-слое. Если два администратора одновременно правят разные поля, второй `replace` запишет студента целиком со старым значением чужого поля — потерянное обновление, от которого Read Committed не защищает. Защищать слияние в ресурсе можно тем, что Merge Patch (RFC 7396) работает над представлением; исправление — метод сервиса `patch(isuId, changes)` под одной `@Transactional` с `@Version` или `ETag` и `If-Match` с ответом 412. Одна `@Version` дыру не закроет: `replace` заново читает студента и сравнит уже свежую версию.

- [ ] `RuntimeException` выбран потому, что `@Transactional` не откатывает транзакцию на unchecked
