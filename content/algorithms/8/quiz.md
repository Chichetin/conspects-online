## Лёгкий уровень

### Вопрос 1

Что такое корзина (бакет) хеш-таблицы?

- [ ] Отдельный отсортированный массив, в котором хранятся все ключи таблицы
- [x] Ячейка массива хеш-таблицы, в которую раскладываются элементы
- [ ] Функция, которая по ключу вычисляет номер ячейки массива
- [ ] Значение, которое хранится в таблице по заданному ключу

**Разбор:** хеш-таблица — массив ячеек плюс правило, которое по ключу сразу называет ячейку. Ячейку этого массива и называют корзиной, или бакетом. Функция, которая называет номер ячейки, — это хеш-функция, а то, что хранится по ключу, — значение.

**Где в конспекте:** раздел 1 «Зачем нужны хеш-таблицы: бейджики по корзинам»

### Вопрос 2

За какое время хеш-таблица в среднем кладёт и находит значение по ключу?

- [ ] $O(n)$
- [ ] $O(\log n)$
- [x] $O(1)$
- [ ] $O(n \log n)$

**Разбор:** по ключу сразу вычисляется номер ячейки, и переход к ней стоит константу, поэтому в среднем — $O(1)$. $O(n)$ — линейный поиск по неотсортированному списку, $O(\log n)$ — бинсёрч по отсортированному массиву или дерево поиска.

**Где в конспекте:** раздел 2 «От списка и дерева к константе: прямая адресация»

### Вопрос 3

Каким требованиям должна удовлетворять хорошая хеш-функция? Выберите все верные.

- [x] Один и тот же ключ всегда даёт один и тот же адрес
- [ ] Разные ключи никогда не попадают в одну ячейку
- [x] Разные, даже близкие ключи распределяются по всем ячейкам
- [ ] Ключи раскладываются по ячейкам в порядке возрастания
- [x] Хеш считается быстрее, чем обычный поиск элемента

**Разбор:** три требования — детерминированность, равномерность и быстрый расчёт. Отсутствия коллизий не требуют: никакая функция его не гарантирует, хорошая лишь делает их редкими. Порядок ключей хеш-таблица вообще не обещает — для этого есть дерево поиска.

**Где в конспекте:** раздел 3 «Хеш-функции: хорошие и плохие»

### Вопрос 4

Какие типы данных Python в первую очередь подходят в качестве ключей хеш-таблицы (`Hashable`)?

- [ ] Изменяемые коллекции, например списки, чтобы ключ можно было дополнять
- [ ] Только целые числа, потому что хеш — это остаток от деления
- [ ] Любые объекты, если хеш-функция для них считается быстро
- [x] Неизменяемые типы, например строки и `int`

**Разбор:** `Hashable` — это в первую очередь неизменяемые типы: ключ не может «вдруг» поменять значение, поэтому и его хеш остаётся прежним, и значение по нему находится. Строки тоже годятся — их переводят в число через коды символов. Ограничиваться целыми числами не нужно: остаток от деления — лишь простейшая хеш-функция.

**Где в конспекте:** раздел 3 «Хеш-функции: хорошие и плохие»

### Вопрос 5

Что называют коллизией в хеш-таблице?

- [ ] Ключ, который вставили в таблицу повторно с новым значением
- [x] Случай, когда два разных ключа получили один и тот же хеш
- [ ] Удаление ключа, после которого в ячейке остаётся пустота
- [ ] Переполнение таблицы, когда свободных ячеек больше нет

**Разбор:** коллизия — $h(k_1) = h(k_2)$ при $k_1 \ne k_2$: разные ключи претендуют на одну ячейку. Повторная вставка того же ключа — обычное обновление значения, а не коллизия. Переполнение таблицы — отдельная проблема, её решают ростом таблицы и рехешированием.

**Где в конспекте:** раздел 4 «Коллизии и метод цепочек»

### Вопрос 6

Что хранится в каждой ячейке хеш-таблицы при разрешении коллизий методом цепочек?

- [ ] Ровно одна пара «ключ — значение» или пустота
- [ ] Номер следующей свободной ячейки для пробирования
- [x] Список пар «ключ — значение», чьи ключи попали в эту ячейку
- [ ] Метка, что элемент из ячейки удалён

**Разбор:** в методе цепочек ячейка становится списком: пара с совпавшим хешем дописывается в конец цепочки, и в одну ячейку помещается сколько угодно элементов. Одна пара на ячейку и поиск свободной соседней — это открытая адресация, метка удаления — её надгробие.

**Где в конспекте:** раздел 4 «Коллизии и метод цепочек»

### Вопрос 7

Что такое tombstone («надгробие») в хеш-таблице с открытой адресацией?

- [x] Метка на месте удалённого элемента, через которую поиск идёт дальше
- [ ] Пустая ячейка, на которой поиск останавливается и решает, что ключа нет
- [ ] Ячейка, в которой сходятся ключи с одинаковым хешем
- [ ] Метка ключа, время жизни которого в таблице истекло

**Разбор:** надгробие ставят вместо удалённой пары: оно говорит «здесь было значение, двигайся дальше». На настоящей пустоте поиск, наоборот, останавливается. Истечение времени жизни — это TTL в кешах, к открытой адресации оно не относится.

**Где в конспекте:** раздел 5 «Открытая адресация и tombstone»

### Вопрос 8

Что показывает коэффициент заполнения (load factor) $\alpha$ хеш-таблицы?

- [ ] Долю ячеек таблицы, которые остаются пустыми
- [ ] Длину самой большой цепочки в таблице
- [ ] Число коллизий, случившихся при вставке ключей
- [x] Сколько элементов в среднем приходится на одну ячейку

**Разбор:** $\alpha = n/m$, где $n$ — число положенных элементов, $m$ — число ячеек (capacity). Это мера того, насколько забита таблица. Длина самой большой цепочки определяет стоимость поиска в методе цепочек, но коэффициентом заполнения не является.

**Где в конспекте:** раздел 6 «Коэффициент заполнения и рехеширование»

### Вопрос 9

Какую запись вытесняет LRU-кеш, когда место кончилось?

- [ ] Ту, к которой обращались реже всего
- [x] Ту, к которой дольше всех не обращались
- [ ] Ту, которую положили в кеш последней
- [ ] Ту, у которой истекло время жизни

**Разбор:** LRU — least recently used: каждое обращение делает ключ самым свежим, а вытесняется ключ с «давнего» края, к которому дольше всех не обращались. Вытеснение по счётчику частоты — это MRU в варианте лекции, по истечении времени жизни — TTL.

**Где в конспекте:** раздел 7 «Кеши на хеш-таблице: LRU, MRU и TTL»

### Вопрос 10

Что `OrderedDict` добавляет к обычному словарю?

- [ ] Сортировку ключей по возрастанию для запросов «больше / меньше»
- [x] Порядок элементов, по умолчанию — порядок вставки
- [ ] Вытеснение старых записей при нехватке места
- [ ] Разрешение коллизий методом цепочек вместо открытой адресации

**Разбор:** `OrderedDict` — хеш-таблица плюс дополнительный список, по которому элементы можно пройти «сверху вниз» в том порядке, в каком их положили. Это не сортировка по значению ключа: для запросов «больше / меньше» по-прежнему нужно дерево поиска или отсортированный массив.

**Где в конспекте:** раздел 8 «Что выбрать: сводка и `OrderedDict`»

### Вопрос 1

Бейджики разложены по 26 корзинам массива по первой букве имени, от корзины 0 (A) до 25 (Z). Почему компьютеру одинаково быстро положить бейджик и в корзину 0, и в корзину 25, хотя человеку до 25-й идти дальше?

- [ ] Корзины упорядочены по алфавиту, поэтому нужная находится бинсёрчем
- [ ] Массив из 26 ячеек маленький, поэтому его перебор почти ничего не стоит
- [x] У массива произвольный доступ: переход к любой ячейке по индексу стоит одинаково
- [ ] Хеш-функция кладёт частые буквы в начало массива, а редкие — в конец

**Разбор:** по ключу сразу вычисляется номер корзины, а переход к ячейке массива по известному индексу стоит константу, где бы она ни находилась. Поэтому и положить бейджик, и найти его — один шаг. Ни бинсёрча, ни перебора здесь нет: в этом и состоит выигрыш хеш-таблицы.

**Где в конспекте:** раздел 1 «Зачем нужны хеш-таблицы: бейджики по корзинам»

### Вопрос 2

Учебная таблица с прямой адресацией: массив из 10 слотов, $h(k) = k \bmod 10$, в каждом слоте лежит одно значение. В таблице уже лежат ключи 15, 22 и 8. Что произойдёт при записи ключа 35?

- [x] Ключ 35 запишется в слот 5 и затрёт ключ 15
- [ ] Ключ 35 запишется в следующий свободный слот 6
- [ ] Слот 5 станет списком из двух ключей, 15 и 35
- [ ] Таблица увеличится до 20 слотов, и ключи разложатся заново

**Разбор:** $35 \bmod 10 = 5$ — тот же слот, что у 15. В простом варианте прямой адресации запись идёт прямо в `table[h(k)]`, поэтому сосед затирается. Поиск следующего свободного слота — это открытая адресация, список в слоте — метод цепочек, рост таблицы — рехеширование: всё это способы справиться с такой ситуацией, а не поведение прямой адресации.

**Где в конспекте:** раздел 2 «От списка и дерева к константе: прямая адресация»

### Вопрос 3

Что при прямой адресации приходится решать заранее, в отличие от обычного списка?

- [ ] В каком порядке отсортировать ключи перед вставкой
- [x] Сколько ячеек выделить под ожидаемое число элементов
- [ ] Какой длины будет каждый ключ
- [ ] Сколько элементов можно будет потом удалить

**Разбор:** обычный список выделяет память по мере надобности, а массив ячеек — пространство признаков — нужно выделить сразу: до 100 элементов — делим на 100, до 1000 — на 1000. Сортировать ключи как раз не нужно: функция $h$ сама говорит, куда положить элемент и откуда его взять.

**Где в конспекте:** раздел 2 «От списка и дерева к константе: прямая адресация»

### Вопрос 4

Строку нужно превратить в число, чтобы выбрать для неё ячейку. Какие утверждения о способах сделать это верны? Выберите все верные.

- [x] Сумма кодов `ord` не учитывает порядок: «кот» и «ток» получат один хеш
- [x] Склейка кодов в одно число однозначна, но раздувает пространство признаков
- [ ] Полиномиальный хеш учитывает порядок букв и поэтому исключает коллизии
- [x] Длина строки по модулю $m$ отправляет все слова одной длины в один слот

**Разбор:** сумма кодов одинакова для слов из одних и тех же букв, длина строки нарушает равномерность («кот», «ток», «кит», «дом» — все в слоте 3), склейка кодов различает слова, но ради нескольких букв требует огромного пространства. Полиномиальный хеш учитывает и символы, и порядок, но коллизии у него остаются: при $m = 7$ «кит» и «дом» попадают в один слот.

**Где в конспекте:** раздел 3 «Хеш-функции: хорошие и плохие»

### Вопрос 5

Полиномиальный хеш считается так:

```python
def hash_poly(s: str, m: int, p: int = 31) -> int:
    h = 0
    power = 1
    for ch in s:
        h = (h + ord(ch) * power) % m
        power = (power * p) % m
    return h
```

Строка состоит из трёх символов с кодами `ord` 2, 1 и 3 (в этом порядке), $p = 3$, $m = 10$. Чему равен хеш?

**Ответ:** 2 ± 0

**Разбор:** по формуле $h(s) = \left(\sum s[i] \cdot p^{i}\right) \bmod m$:

$$h = (2 \cdot 1 + 1 \cdot 3 + 3 \cdot 9) \bmod 10 = 32 \bmod 10 = 2.$$

Пошагово в коде: $h = 2$, затем $(2 + 3) \bmod 10 = 5$, затем $(5 + 27) \bmod 10 = 2$; остаток на каждом шаге даёт тот же результат. Для той же тройки в обратном порядке (3, 1, 2) получится $(3 + 3 + 18) \bmod 10 = 4$ — веса позиций различают перестановки.

**Где в конспекте:** раздел 3 «Хеш-функции: хорошие и плохие»

### Вопрос 6

Хеш-таблица с цепочками: capacity $= 6$, хеш — `key % capacity`, новая пара дописывается в конец цепочки. Последовательно выполнили `put` для ключей 4, 10, 16, 9, 22, затем `remove(10)`. Сколько сравнений ключей сделает `get(22)` в своей корзине?

**Ответ:** 3 ± 0

**Разбор:** остаток от деления на 6 у ключей 4, 10, 16 и 22 равен 4, у ключа 9 — 3. В корзине 4 цепочка $[4, 10, 16, 22]$; после удаления 10 остаётся $[4, 16, 22]$. `get(22)` проходит 4, затем 16 и только на третьем сравнении находит 22. Поиск стоит $O(k)$ по длине цепочки, а не $O(1)$.

**Где в конспекте:** раздел 4 «Коллизии и метод цепочек»

### Вопрос 7

Таблица `OpenHashMap` (открытая адресация без роста) с `capacity = 7` уже содержит 7 ключей. Что произойдёт при `put` нового ключа?

- [ ] Новый ключ запишется поверх ключа в ячейке $h(k)$
- [ ] Таблица удвоится до 14 ячеек, и ключи разложатся заново
- [ ] Новый ключ допишется в цепочку ячейки $h(k)$
- [x] `put` обойдёт все 7 проб и выбросит `RuntimeError`

**Разбор:** `OpenHashMap` выделена под фиксированный `capacity`, и в каждой ячейке — не больше одной пары. Свободной ячейки нет, поэтому `put` перебирает все `capacity` проб и выбрасывает `RuntimeError("таблица полна")`. Удвоение и перекладка ключей — это `GrowingOpenHashMap`, цепочки — метод цепочек. Именно поэтому нужна таблица, которая растёт сама.

**Где в конспекте:** раздел 5 «Открытая адресация и tombstone»

### Вопрос 8

Открытая адресация с линейным пробированием, capacity $= 7$, $h(k) = k \bmod 7$. В пустую таблицу последовательно кладут ключи 3, 10, 17 и 4. В какой слот попадёт ключ 4?

**Ответ:** 6 ± 0

**Разбор:** у ключей 3, 10 и 17 хеш равен 3, поэтому они занимают слоты 3, 4 и 5. У ключа 4 хеш 4, но слот 4 занят ключом 10, слот 5 — ключом 17, и 4 ложится в слот 6:

$$h(4, 0) = 4,\quad h(4, 1) = 5,\quad h(4, 2) = 6.$$

Это кластеризация: у ключа 4 нет общего хеша с остальными, но он попал в сплошную серию занятых ячеек и удлинил её.

**Где в конспекте:** раздел 5 «Открытая адресация и tombstone»

### Вопрос 9

Таблицу с хешем $h(k) = k \bmod m$ увеличивают с $m = 4$ до $m = 8$. Почему старые ключи нельзя оставить на прежних местах?

- [x] Хеш зависит от $m$, и `get` будет искать ключ в новом слоте, а не в старом
- [ ] Без перекладки в новой таблице останутся надгробия удалённых ключей
- [ ] Ключи нужно заново отсортировать, чтобы поиск остался быстрым
- [ ] После увеличения хеш-функция перестаёт быть детерминированной

**Разбор:** новая таблица — это и новая хеш-функция: делим уже на 8, а не на 4. Ключ 30 при $m = 4$ лежал в слоте 2, а при $m = 8$ его хеш 6 — там его и будет искать `get`. Надгробия при рехеше действительно не переносятся, но это следствие перекладки, а не её причина. Хеш-функция остаётся детерминированной: при фиксированном $m$ ключ всегда даёт один слот.

**Где в конспекте:** раздел 6 «Коэффициент заполнения и рехеширование»

### Вопрос 10

`LRUCache(2)`. Выполнили `put(1, 'a')`, `put(2, 'b')`, `put(1, 'c')`, затем `put(3, 'd')`. Какой ключ будет вытеснен?

- [ ] Ключ 1, потому что его положили в кеш раньше всех
- [x] Ключ 2, потому что к нему дольше всех не обращались
- [ ] Ключ 3 не попадёт в кеш, потому что место кончилось
- [ ] Никакой: кеш увеличится до трёх записей

**Разбор:** в LRU обращением считается и `get`, и `put`. Повторный `put(1, 'c')` сделал ключ 1 самым свежим, и на «давнем» краю оказался ключ 2 — его и вытесняют, чтобы положить 3. Расти кеш не может: это хеш-таблица фиксированного размера, вместо рехеша в ней — эвикция.

**Где в конспекте:** раздел 7 «Кеши на хеш-таблице: LRU, MRU и TTL»

### Вопрос 11

Нужна структура, которая по цене быстро находит ближайший товар дороже заданной цены. Что выбрать?

- [ ] Хеш-таблицу `dict`: поиск по ключу в ней стоит $O(1)$
- [ ] `OrderedDict`, потому что он хранит элементы в порядке
- [x] Дерево поиска или отсортированный массив
- [ ] Хеш-таблицу с цепочками, чтобы близкие цены лежали в одной корзине

**Разбор:** хеш-таблица хороша для точного поиска по ключу, а для запросов «больше / меньше» и «ближайший больший» бесполезна: порядок ключей она не обещает. `OrderedDict` хранит порядок вставки, а не порядок ключей по величине. Для упорядоченных запросов берут дерево поиска или отсортированный массив.

## Сложный уровень

### Вопрос 1

Хеш-таблица обещает поиск по ключу за $O(1)$. Какие доводы о том, когда это обещание перестаёт выполняться, верны? Выберите все верные.

- [x] Если все ключи попали в одну корзину, поиск снова стоит $O(n)$
- [ ] Константа гарантирована всегда, потому что хеш считается за фиксированное время
- [x] Когда коэффициент заполнения растёт, коллизий больше и операции замедляются
- [ ] В худшем случае поиск стоит $O(\log n)$, потому что цепочки упорядочены
- [x] Плохая хеш-функция, например длина строки, сваливает много ключей в одну ячейку

**Разбор:** константа у хеш-таблицы средняя. Она держится, пока хеш-функция равномерно размазывает ключи и таблица не переполнена. Если функция плохая или $\alpha$ велик, ключи скапливаются в одних ячейках, и в пределе поиск становится линейным. Быстрый расчёт хеша лишь приводит к нужной ячейке, а перебор внутри неё он не отменяет. Цепочки ничем не упорядочены, поэтому худший случай — $O(n)$, а не логарифм.

### Вопрос 2

`OpenHashMap` с `capacity = 7`, $h(k) = k \bmod 7$, линейное пробирование. Выполнили `put` для ключей 15, 22, 8, затем `remove(22)`, затем `put(29, 'v29')`. Метод `put` устроен так:

```python
def put(self, key, value):
    first_tomb = None
    for j in range(self.capacity):
        i = (self._h(key) + j) % self.capacity
        cell = self.slots[i]
        if cell is None:
            dest = first_tomb if first_tomb is not None else i
            self.slots[dest] = (key, value)
            self.size += 1
            return
        if cell is _TOMB:
            if first_tomb is None:
                first_tomb = i
            continue
        ...  # ключ совпал — обновляем на месте
```

В какой слот попадёт ключ 29?

**Ответ:** 2 ± 0

**Разбор:** ключи 15, 22, 8 заняли слоты 1, 2, 3; после `remove(22)` в слоте 2 — надгробие. У 29 хеш $29 \bmod 7 = 1$: слот 1 занят ключом 15, в слоте 2 надгробие — его запоминают как `first_tomb = 2` и идут дальше; слот 3 занят ключом 8, слот 4 пуст. На настоящей пустоте ясно, что ключа 29 в таблице нет, и пара кладётся в первое надгробие — слот 2. Ответ 4 получится, если забыть про переиспользование надгробия.

**Где в конспекте:** раздел 5 «Открытая адресация и tombstone»

### Вопрос 3

Открытая адресация, линейное пробирование, $h(k) = k \bmod 7$: в слотах 1, 2, 3 лежат ключи 15, 22 и 8. Ключ 22 удалили, просто записав в слот 2 пустоту `None` вместо надгробия. Какие последствия будут? Выберите все верные.

- [x] `get(8)` вернёт `None`, хотя ключ 8 остался в слоте 3
- [ ] `get(15)` тоже перестанет находить ключ 15
- [x] `put(8, 'new')` запишет ключ 8 в слот 2, и в таблице будет два ключа 8
- [ ] Хеш ключа 8 изменится, потому что изменилось содержимое таблицы

**Разбор:** поиск останавливается на первой пустоте. Пробы ключа 8 идут 1 → 2, и в слоте 2 теперь `None`, поэтому `get` решает, что ключа нет. По той же причине `put` не дойдёт до слота 3 и положит 8 в слот 2 — получится дубликат. Ключ 15 лежит в своём слоте 1 и находится с первой пробы. Хеш-функция от содержимого таблицы не зависит: она детерминирована. Поэтому на месте удалённого элемента ставят надгробие, через которое поиск проходит дальше.

### Вопрос 4

`GrowingOpenHashMap(capacity=4, threshold=0.7)` — открытая адресация с линейным пробированием и хешем `key % capacity`. Рехеш устроен так:

```python
def _rehash(self):
    old = [c for c in self.slots if c is not None and c is not _TOMB]
    self.capacity = self.capacity * 2
    self.slots = [None] * self.capacity
    self.size = 0
    for k, v in old:
        super().put(k, v)

def put(self, key, value):
    if self.load_factor > self.threshold:
        self._rehash()
    super().put(key, value)
```

В пустую таблицу последовательно кладут ключи 3, 7, 11, 2. В каком слоте окажется ключ 3 после всех вставок?

**Ответ:** 4 ± 0

**Разбор:** при capacity 4: ключ 3 — в слот 3; у 7 хеш 3, занято → слот 0; у 11 хеш 3, слоты 3 и 0 заняты → слот 1. Перед вставкой 2 коэффициент $\alpha = 3/4 = 0{,}75 > 0{,}7$ — рехеш до 8 слотов. Список `old` собирается в порядке слотов: 7 (слот 0), 11 (слот 1), 3 (слот 3). Заново: $7 \bmod 8 = 7$, $11 \bmod 8 = 3$, у 3 хеш тоже 3, но слот занят ключом 11 → слот 4. Ключ 2 ложится в слот 2. Ответ 3 получится, если перекладывать ключи в порядке их исходной вставки, а не в порядке слотов.

**Где в конспекте:** раздел 6 «Коэффициент заполнения и рехеширование»

### Вопрос 5

Таблица `GrowingOpenHashMap` создана с capacity $= 100$ и порогом $0{,}75$. Перед каждой вставкой она проверяет, превышает ли $\alpha$ порог, то есть больше ли `size`, чем $0{,}75 \cdot$ capacity, и если да — удваивается. В неё по одному кладут 600 разных ключей. Сколько раз сработает рехеш?

**Ответ:** 3 ± 0

**Разбор:** порог в штуках при capacity 100 — 75 элементов, при 200 — 150, при 400 — 300, при 800 — 600. Рехеш срабатывает перед вставкой 77-го ключа (size 76 > 75, capacity → 200), 152-го (151 > 150, → 400) и 302-го (301 > 300, → 800). Перед 600-м ключом size = 599, это не больше 600, и четвёртого рехеша нет. Если бы размер сразу задали как $m \approx n/\alpha = 600 / 0{,}75 = 800$, все три перекладки удалось бы сэкономить.

### Вопрос 6

Два кеша ёмкостью 2 — `LRUCache` и `MRUCache` в варианте лекции (со счётчиком частоты `freq`, который растёт и при `put`, и при `get`). В каждом выполнили одну и ту же последовательность: `put(1)`, `put(2)`, `get(1)`, `get(1)`, `get(2)`, затем `put(3)`. Какой ключ вытеснит каждый из кешей?

- [ ] LRU вытеснит ключ 2, MRU вытеснит ключ 1
- [ ] Оба кеша вытеснят ключ 1
- [x] LRU вытеснит ключ 1, MRU вытеснит ключ 2
- [ ] Оба кеша вытеснят ключ 2

**Разбор:** LRU смотрит на то, как давно было последнее обращение. Последним трогали ключ 2, поэтому на «давнем» краю — ключ 1, его и вытесняют. MRU в варианте лекции смотрит на частоту: $\text{freq}(1) = 1 + 2 = 3$, $\text{freq}(2) = 1 + 1 = 2$. У ключа 2 счётчик меньше, поэтому вытеснят его. Одна и та же история обращений даёт разные решения, потому что правила вытеснения разные.

### Вопрос 7

Кеш создан как `MRUCache(2, ttl=5.0)`. Какие утверждения о нём верны? Выберите все верные.

- [x] Запись, положенную в момент 0 и прочитанную `get` в момент 3, в момент 6 уже не найти
- [ ] Частые `get` защищают запись от истечения TTL, как и от вытеснения по частоте
- [x] `MRUCache(2, ttl=0)` выбросит `ValueError` при создании
- [ ] TTL обычно задают отдельно для каждого ключа при его вставке
- [x] TTL — свойство записи: истёкшую запись удаляют независимо от её счётчика обращений

**Разбор:** TTL — время жизни записи: по его истечении запись удаляют независимо от порядка и частоты обращений, а `get` срок жизни не продлевает. Поэтому чтение в момент 3 не спасает запись, положенную в момент 0, — в момент 6 её уже нет. Неположительные ёмкость или TTL — ошибка `ValueError` в конструкторе. Обычно TTL задают один на всю структуру при инициализации; реализации с отдельным временем жизни у каждого ключа бывают, но редко.

### Вопрос 8

Сервис работает на устройстве с жёстким лимитом памяти и хранит до 1000 записей с целыми ключами; записи иногда удаляют. Какие решения о хеш-таблице для него верны? Выберите все верные.

- [x] Взять открытую адресацию: память выделяется заранее и контролируется, без списков в ячейках
- [ ] Взять метод цепочек: ему не нужно заранее угадывать размер, память добавляется по ходу
- [x] Сразу задать размер порядка $n/\alpha$, например $1000 / 0{,}5 = 2000$ ячеек, чтобы не рехешировать
- [ ] Поднять порог $\alpha$ до 1, чтобы каждая ячейка была занята и память не пропадала
- [x] При удалении из таблицы с открытой адресацией ставить надгробие, а не очищать ячейку

**Разбор:** при нехватке памяти чаще выбирают открытую адресацию: все ключи живут в заранее выделенном массиве, и его размер известен. Метод цепочек действительно не требует угадывать размер, но именно поэтому его память растёт бесконтрольно — при жёстком лимите это минус. Число элементов известно, поэтому размер задают сразу, $m \approx n/\alpha$. Порог около 1 ведёт к деградации: коллизий всё больше, и пробы становятся длинными. Удаление в открытой адресации требует надгробий.

### Вопрос 9

Ключи — все строки из строчных русских букв длиной до 10 символов, таблица — на $m = 1000$ ячеек. Какие доводы о коллизиях в такой таблице верны? Выберите все верные.

- [x] Хеш-функции без коллизий на этом наборе не существует: возможных ключей больше, чем ячеек
- [ ] Полиномиальный хеш с $p = 31$ исключит коллизии, потому что учитывает порядок букв
- [x] Хорошая хеш-функция лишь делает коллизии редкими, поэтому таблица должна уметь их разрешать
- [ ] Коллизий не будет, если хеш-функция детерминирована
- [x] Склейка кодов `ord` различает все строки, но требует пространства намного больше 1000 ячеек
